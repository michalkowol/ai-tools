Inbox: skip small PRs and estimate PRs by changed files

Capture creates no separate cards for small PRs waiting for review, because the recurring "code review" card in Notion covers them. The estimate (🍅) of a PR follows from the number of changed files.

Context

The user has a recurring code review card in Notion whose body links to https://github.com/pulls/reviews. It already covers all small PRs, so separate Inbox cards for them are noise. Large PRs still need their own card to plan time for them, and the estimate should follow from the PR size instead of guessing.

Decision log

How does the number of changed files translate into tomatoes?

1–3 files: 0.25 · 4–9: 0.5 · 10–19: 1 · 20–39: 2 · 40+: 3 x 🍅. Fine steps at the bottom, where most PRs are. 1–9 files: 0.5 · 10–29: 1 · 30+: 2 x 🍅. Simpler, but does not tell a one-liner from a medium PR. Thresholds as in A, one step up for many lines (e.g. > 500 changes); lockfiles and generated files do not count. More precise, but more rules to maintain.

Recommended option accepted. Most PRs are small, so the lower thresholds are denser.

Which PR is "small" and gets no separate card?

By the thresholds from Q1 (in A: fewer than 10 files). Separate cards only for reviews that need planned time. Only the smallest (in A: 1–3 files). More cards in the Inbox. Separate cards only for large PRs (in A: 20+ files). Few cards, but an hour-long review disappears into the recurring card.

Recommended option accepted. A separate card only for reviews that need planned time (10+ files per D1).

Which PRs does skipping cover?

PRs waiting for my review (direct and through a team), from bots too. My PRs (my_prs: changes to make, failing CI) always get a card, because the recurring card does not cover them. Small my_prs too. Fewer cards, but e.g. failing CI on my PR can be missed.

Does a small PR waiting for review still get a card in some situation?

All small ones go to the recurring card, which leads to github.com/pulls/reviews, where they are all visible. The simplest rule. E.g. waits > 2 workdays. A guard against a forgotten PR, but a rule with a number. A direct request (not through a team) always gives a card. Some small PRs come back to the Inbox anyway.

Recommended option accepted. The recurring card leads to pulls/reviews, where all small PRs are visible.

What does capture do with a skipped small PR?

The answer says "N small PRs left for the code review card". The URL does not go into the registry, so when the PR grows above the threshold, the next capture creates a card for it. The skill does not change the recurring card. The URL goes into the registry as for a card, so the PR does not come back for 30 days, even if it grows. Adds a bullet with a link to the PR in the code review card body. A list in Notion, but the card grows and duplicates pulls/reviews.

Recommended option accepted. A PR that grows above the threshold gets a card in a later capture; the skill does not change the recurring card.

Where does processing get the number of files for the estimate?

Capture appends the size: PR org/shop#412 by alice, waiting 26 h, 7 files (+120/−30). Processing computes the estimate from this line, without running gh again. The card has Estimate from the thresholds at once. One source of truth in Notion, but breaks the rule "capture sets only Status, Category, URL". Processing calls worklog github again. Always the current size, but slower and duplicate queries.

Recommended option accepted. The size is already in the capture data, processing does not need to ask GitHub a second time.

What about cards for small PRs that are already in the Inbox?

Processing proposes Trash with the reason "small PR, covered by the code review card". The user can change it on the page. The rule applies only to new captures; old cards are processed normally.

Recommended option accepted. Old small-PR cards go away by the same rule, and the user can change the proposal on the page.

Skip small PRs that you authored too?

Only small PRs by others waiting for review are skipped. Your action on your own PR (fixes, CI) is not code review, so it does not get lost in the recurring card. Fewer cards, but e.g. failing CI or a change request on a small own PR does not reach the Inbox.

Recommended option accepted. The recurring card covers only reviews of other people's PRs.
