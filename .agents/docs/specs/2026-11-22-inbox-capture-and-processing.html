Inbox: capture into Notion and fast processing

A new skill in daily-workflow: collect in one place (status Inbox in the Notion ✅ GTD database) everything from Slack, GitHub and Gmail that should land in the inbox, then process those cards as fast as possible.

Context

The briefing reads Slack, GitHub and Gmail, but only to plan the day: nothing of it stays in the GTD system. Things that need action are spread over several apps. Goal: one place (status Inbox in Notion ✅ GTD) that receives everything it should, followed by fast GTD processing of the cards, so the Inbox ends up empty.

Facts

Plugin

  • The plugin has two skills, briefing and worklog, sharing the CLI scripts/worklog.py with commands such as dates, github, render-plan. plugins/daily-workflow/scripts/worklog.py
  • worklog github already returns review_requested, team_repo_prs and my_prs. skills/briefing/references/sources.md
  • The briefing already has the Slack queries (DMs, channels, mentions, is:saved) and the Gmail query, plus the rule "a reply or a reaction = handled". sources.md sections Slack and Gmail
  • The config has [notion].view_inbox, but no skill uses it. config.example.toml
  • Per-run state fits into ~/.ai/worklog/state/. README, Worklog layout
  • render-plan renders a fixed HTML template from JSON, without JavaScript, escapes text and prints the open … command for the host. scripts/wl/plan.py
  • The spec components store answers in localStorage and generate a prompt to copy. .agents/docs/specs/assets/global-components.js
  • A page opened on the host through file:// cannot write a file into ~/.ai/worklog. A downloaded file lands in the host's Downloads, outside the container. browser model, README (open command on the host)

Notion

  • Status has the value Inbox; a card without Status, Category or Estimate lands in the Inbox view. gtd-rules.md
  • Current rule: never change Notion without consent, never create new projects, tags and projects only from existing options. gtd-rules.md Rules for changes
  • The card URL field is available in SQL as userDefined:URL; SQL mode has an hourly limit. gtd-rules.md Connection

Connectors

  • Slack search has no unread filter; the connector has no tool to mark messages as read. It has slack_send_message_draft and slack_add_reaction. Slack MCP tool descriptions
  • Gmail is not signed in in this session (only authenticate is available). MCP tool list

Out of scope

  • Changes to the briefing: capture runs manually only (D2).
  • Jira as an Inbox source (D3).
  • Draft replies and reactions in the sources (D10, D14).
  • Sending messages, emails or PR comments.
  • The GTD model in Notion (statuses, fields).

Decision log

How to split the skill?

/daily-workflow:inbox captures and immediately proposes the processing, /daily-workflow:inbox process only processes. One place for the rules and the state. E.g. capture and process. Clearer names, but duplicated source and Notion rules. The briefing captures into the Inbox first. Fewer commands, but the briefing gets longer and the inbox cannot be run on its own during the day.

One place for the source rules and the cursor state. Capture flows straight into processing, and process is enough when only processing is needed.

When does capture run?

Only the command. Full control, no background cost. The briefing captures first (without processing), then plans with the full picture. The Inbox is always fresh, but it runs without the user and costs tokens.

Full control and no background token cost.

Which sources to capture?

Only threads that want something from the user, not every post. Changes requested, failing CI. They usually arrive through the sprint anyway, easy to duplicate.

Everything that can ask something of the user during the day. Jira stays out, because sprint tickets reach Notion through the briefing and would create duplicates.

What does "unread" mean on Slack?

A cursor with the time of the last run in ~/.ai/worklog/state/. A message drops out if the user replied in the thread or added any reaction (the same rule as in the briefing). No state, but with several runs a day the same items come back (only deduplication stops them). Nothing is missed, but a lot of noise to process.

The connector has no read state, so a cursor plus the briefing rule (reply or reaction = handled) is the closest approximation.

What is "important email"?

As in the briefing: in:inbox category:primary is:unread, without GitHub/Jira notifications; the model judges whether someone wants something. is:important is:unread. Simple, but Gmail also marks newsletters as Important. Full control, but needs manual starring in Gmail.

The same query as the briefing, without notification mail. The model keeps only mail where someone wants something.

How to avoid duplicates?

Before creating, check whether any card (not only in the Inbox) has the same link to the message, PR or email. Also works after processing. A file with the IDs of captured items. Faster, but does not know about cards added by hand. The registry as a fast filter, the URL in Notion as the final check.

The local registry quickly filters known items, and the URL check in Notion also catches cards added by hand and works after processing.

How many cards per item?

Each card is one decision during processing. Fewer cards, but one card can hold several different actions. Renovate and similar grouped, the rest separate.

Each card is one decision during processing.

Does creating cards in the Inbox need consent?

The Inbox is unprocessed by definition, so creating cards there is a safe exception. No edits of existing cards without consent. Consistent with the current rule, but in practice it is processing twice.

The Inbox by definition holds unprocessed items, so creating cards there is a safe exception to the consent rule. Existing cards are never changed without consent.

What does a card contain?

E.g. "Reply to Alice about the API contract"; the body holds a short verbatim quote, author, time, channel. Source URL in the URL field. Category Work, English. PR title / email subject / start of the message. Less interpretation, slower to process.

An action title speeds up processing, and the quote and the link give the context without opening the source.

Should anything change in the sources after capture?

The plugin never sends anything. Slack cannot mark messages as read anyway. E.g. 📥 on the captured message, visible to everyone in the channel. Replaces the cursor from Q4.

The plugin never sends anything, and Slack cannot mark messages as read anyway.

What should processing look like?

Each question is one card, the AI proposal is the first option (Recommended), the rest are alternatives. Enter, Enter, Enter. All cards at once, answers pasted back as a prompt like in the specs. Fast review of many cards, but switching windows. Proposals in a table, the user answers "ok" or corrections like "3: someday".

All cards are visible at once, which is faster for a large Inbox. Answers come back as a pasted prompt like in the specs. Details in D17–D21.

What does the AI propose for a card?

Status, Estimate, priority, Reminder / Due Date, optionally Project from existing options. Approved with one click. Faster to read, but a card without Estimate falls back into the Inbox view (rule from gtd-rules).

One-click approval only works with a full proposal. A card without Estimate falls back into the Inbox view.

Which GTD outcomes are available for a card?

The topic goes into the body of the person's card, the Inbox card is archived. The current rule forbids creating projects.

The standard GTD outcomes. Creating projects stays forbidden by the existing rule.

What happens on "done now"?

The user does it in Slack / GitHub / Gmail. A draft in Slack (slack_send_message_draft) or Gmail, nothing is sent. Faster, but longer processing.

The user acts in the source app; the plugin sends and drafts nothing.

Which cards to process?

Including cards added by hand and from the phone. Inbox zero. Faster, but manual cards stay.

Inbox zero includes cards added by hand and from the phone.

In what order are cards shown?

Someone is waiting (a direct question, a review), then cards with a deadline, then the rest, oldest first. Oldest first, predictable. Slack, PRs, email. Easier to keep the context.

Unblocking others first, then deadlines, then the rest oldest first.

How do the answers from the page get back into the session?

Like in the specs: a Copy button, paste into the session. Answers in localStorage, so a page reload keeps them. Works through file://. Less text in the chat, but the file lands in the host's Downloads and has to be moved into the container. Saved with one click, but needs an exposed port and a background process.

The only option that works from file:// on the host without moving files or running a server.

What can be changed on a card on the page?

A radio with the outcome (D13), below it Estimate, priority, Reminder / Due Date, Project prefilled with the proposal and editable. A text note. The AI sets the fields, corrections only through the note. Faster, less control. Fastest, but every correction goes through the note.

The proposal makes approval one click, and editable fields allow corrections without writing notes.

Who renders the page?

The skill writes a JSON with the cards and proposals, a new command worklog render-inbox produces the HTML (like render-plan). Content from Slack and email is escaped, the look is always the same. No new code, but a risk of injecting source content and an inconsistent look.

Escaping untrusted source content and a stable form need a fixed template, the same pattern as render-plan.

Apply the pasted answers immediately?

After pasting, the agent changes the cards and shows a short summary. Cards without an answer stay in the Inbox. An extra safeguard, but the same thing a second time.

Filling in the form is an explicit approval, so the consent rule for Notion changes is met.

What about cards that do not follow the Notion rules?

The AI proposes a better title as an editable field, applied together with the outcome. Processing only changes fields, the title stays.

Manual cards often have vague titles; a proposed action title is approved in the same click.

How long to keep the local registry of captured items?

Older items drop out through the cursor from D4 anyway, and the file does not grow. Full history in the Worklog git, the file grows.

The cursor already excludes older items, so 30 days is enough as a fast filter (D6).
