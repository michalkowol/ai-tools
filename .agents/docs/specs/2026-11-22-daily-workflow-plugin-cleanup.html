Publishing the daily-workflow plugin in the public marketplace

Where the daily-workflow plugin lives, how to remove private and company data from it before the first commit to the public repo, and how to simplify its documentation.

Context

The daily-workflow plugin (Work Logger and Daily Briefing) started as a private tool and was moved into the marketplace next to mk. The marketplace repo is public, and the plugin's config, skills and tests hold data from a private Notion workspace, the company name, a Jira project key and names of colleagues. The files are staged but not committed yet, so they can be cleaned without rewriting history.

Facts

Repo and plugin

  • The marketplace repo is public. gh repo view --json visibility
  • The plugin lives in plugins/daily-workflow and is a separate marketplace entry. .claude-plugin/marketplace.json
  • The plugin has no commit yet, its files are only staged. git status, git log -- plugins/daily-workflow
  • Hooks run on SessionStart, Stop, PreCompact, SessionEnd and PostToolUse for Bash and MCP, and start claude -p with Haiku every 15 minutes of work. hooks/hooks.json, scripts/wl/collector.py
  • This session already removed dead code (the fallback TOML parser, unused CLI options), references to decisions in a spec outside this repo and outdated instructions (the launcher patch). Tests pass. session 2026-11-22

Private and company data

  • config.example.toml holds the database URL and 6 view or data source IDs of a private Notion workspace, the company Jira URL, the project key and example channel names. config.example.toml sections [notion], [worklog], [slack]
  • The local ~/.ai/worklog/config.toml already exists with the real Notion IDs, so the example is only needed on first install. ~/.ai/worklog/config.toml
  • Colleagues' names appear in examples in plan-schema.md, gtd-rules.md and the tests. skills/briefing/references/*.md, tests/test_worklog.py
  • Names of recurring cards from the private Notion, in Polish, appear in gtd-rules.md and plan-schema.md. gtd-rules.md section Workday plan
  • The Jira project key is hardcoded in the briefing rules, sources.md, the example in the summarizer prompt, the worklog skill, the README and the tests. The code reads keys only from [worklog].jira_project_keys. skills/briefing/SKILL.md, sources.md, scripts/wl/summarizer.py, scripts/wl/core.py
  • [notion].jira_base_url is read only by the skills, the code does not use it. grep jira_base_url scripts

Out of scope

  • The GTD model in Notion (statuses, priorities, estimates): it describes a way of working and holds no data.
  • Author and email in plugin.json: the same as in mk and already public.
  • Changes to the behaviour of the Work Logger and the briefing.

Decision log

Should daily-workflow stay a separate plugin or move into mk?

The hooks run on every response and start paid Haiku calls, so they are installed on purpose and can be disabled without touching mk. Own version. One install and one version, but the hooks and the Worklog directory show up wherever mk is installed, also outside the container.

Hooks with side effects and token cost should be opt-in and independently disabled; mk stays a set of stateless skills and commands.

What goes into config.example.toml instead of the real values?

E.g. view://00000000-…, https://example.atlassian.net, ["PROJ"]. The format is visible and nothing is revealed. Safest, but the format has to be guessed. Works right away, but publishes the Notion IDs and the company name.

The real values already live in the local ~/.ai/worklog/config.toml; the example only has to show the format.

How to anonymize the examples in the skills, the tests and the summarizer prompt?

Names like Alice/Bob, the key PROJ-1234, card names in English, no company name. The examples still make sense. Names stay, since without surnames they do not identify people. No change.

A public repo should not name colleagues, the company or the project, and fictional examples teach the model the same thing.

What about rules that assume a specific Jira project?

The skill says "a ticket from [worklog].jira_project_keys" and takes the Jira URL from [notion].jira_base_url. Works for any project. Fewest changes, but the rule still describes one specific project.

The code already reads project keys from the config, so the skills follow the same source instead of a hardcoded name.

Remove the duplication between briefing/SKILL.md and references/?

SKILL.md lists the steps and points to the file. One place to change. The model has the rules at hand even if it does not open the reference file, but they drift apart easily.

One source per rule avoids the two copies drifting apart; SKILL.md already tells the model to read the references first.
