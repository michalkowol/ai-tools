Inbox: one entry at a time, built from Web Components

A new Inbox processing page in daily-workflow: one entry at a time, the AI proposal accepted by default, an entry can be split into several cards, Gmail-like shortcuts. The page is built from custom elements in the style of the html-spec plugin.

Context

The first version of the Inbox processing page (previous spec, D11, D18) is one long form with all cards at once. With 27 entries it is too slow. The user designed a prototype with the agent: one entry at a time, the AI proposal accepted by default, only what is wrong gets corrected, and an entry can become several cards. This spec brings the prototype into the plugin and settles how to build the page from Web Components so that a review of the page is about content, not formatting.

The behaviour, look, shortcuts, proposal rules and apply rules are already decided in the brief (plan/PROMPT.md, summarized in Facts). Implement them as written there, except where a decision below says otherwise.

Decision log

In what form does the per-run HTML carry the content?

E.g. <inbox-entry entry-id age waiting><inbox-card outcome="next" estimate="1 x 🍅" …>Title</inbox-card></inbox-entry>. Reviewing the per-run HTML means reading content; the renderer escapes every value with html.escape. The JSON file in inbox/ stays the source of truth for apply. As in the brief. One data path, but reviewing the per-run HTML means reviewing JSON, not the page. The components read the markup, the JSON is only for the prompt. Two sources of the same content on the page.

The same pattern as html-spec: the generated page reads as content. This replaces the brief's §10 point "page JSON in a <script type="application/json">"; the other §10 guarantees (escaping, http(s) links only, ordering in the renderer) stay.

How does the page get its CSS and components?

render-inbox overwrites ~/.ai/worklog/inbox/assets/inbox.css and inbox-components.js with the plugin's version, and the page links them relatively (like .agents/docs/specs/assets/). The per-run HTML stays small; old pages also get the new components, so the page declares its format version in a <meta>. A self-contained file frozen at its version, but large, and the review mixes formatting with content. No copying, but the plugin path exists only in the container; on the host the page does not load.

The only option that keeps the per-run HTML small and works from file:// on the host.

Light DOM or Shadow DOM?

Like html-spec: the components render plain markup with classes, the whole look is in one CSS file, easy to review and to test in a browser. Full isolation ("own styles" in the brief), but the CSS is spread over JS classes and tokens have to be passed as custom properties.

Consistent with html-spec, and one stylesheet keeps the look reviewable in one place.

How to test the page logic?

The apply line, fields per status, date options and the Keep rule in a file without DOM, exposed on globalThis. A node --test test loads it through vm; the Python unittest runs it and skips when node is missing. Plus renderer tests in Python. No new tool, but the apply-line format (generated in JS) has no automated test. Tests real keys and DOM, but a heavy dependency the repo does not have.

The apply line is the contract with the skill and must be tested; node is already in the container and needs no dependencies.

What does Keep on the first card of a split entry mean?

Card 1 = Keep: the original stays in the Inbox, the other cards are created as new. The apply line keeps the position ({"outcome":"keep"} in place 1). Like the prototype. A simpler line, but the original's title and status are changed by a card other than the one shown first.

What the user sees as card 1 is what happens to the original page.

Agenda without a chosen person?

Without a choice the card is incomplete: the summary marks it, and apply skips that card and reports it. Always complete, but easy to add the topic to the wrong person.

A silent default puts topics on the wrong person's card.

Does the renderer read the old JSON format (one proposal)?

A few lines of code; the existing file with 27 entries in ~/.ai/worklog/inbox/ opens in the new view. Less code; the old file has to be generated again with process.

Less code; the old file is regenerated with process.

What about the plan/ directory (brief and prototype)?

The spec describes the behaviour without private data; examples in processing.md and the tests are fictional (Alice, org/shop#412, PROJ-1234). The prototype stays as a reference in the repo, but it has to be cleaned and maintained next to the real page. Nothing is lost, but an ignored directory for private files in a public repo.

The repo is public, and the brief's examples (§8, §5) name real people, repos, tickets and a project.

Where do the style tokens (colours, fonts) come from?

The same values as in html-spec, copied. The plan page (plan.py) stays unchanged. One source of colours in the plugin, but it needs a rework of the plan page, which is not part of this change.

Keeps the change inside the inbox page.
