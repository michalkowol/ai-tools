Inbox: Slack To-dos as a source, a reading list and a local knowledge base

Capture picks up what was added to To-dos in Slack, processing splits it into tasks, things to read and important information, and a knowledge mode builds a local knowledge base from the to-dos and the followed channels.

Context

The user wants the Inbox to also catch what was added to To-dos in Slack, and asks to check how it can be fetched. They also want an approach to what they save "for later": sometimes these are tasks, sometimes important information, and sometimes interesting articles or messages.

Round 1 added a requirement: at the very beginning go through all to-dos and build a knowledge base from them in several md files. The first step is to decide how many files are needed, the second is to assign the items to the files.

Round 2 added another: the knowledge should come from various sources, that is from the to-dos, but also from messages in channels.

Facts

Slack

  • Since October 2026 the Later tab is replaced by To-dos (a personal task list) and the Saved section in Home (material to keep). Old Later items with a reminder became to-dos, the rest went to Saved. Slack Help: Later is now To-dos; Save messages and files for later
  • A to-do is "In-progress" or "Completed", has an optional reminder and can be cleared from the list. A to-do can also be added without a message, by typing it in the tab. Slack Help: Later is now To-dos
  • There is no public API for Later, To-dos or Saved. stars.list does not reflect saved items and is to be retired. Slack changelog 2023-07; Slack feature retirements

Slack connector (tests from 2026-11-27)

  • The connector has no tool for to-dos or saved items; what is left is the search slack_search_public_and_private with modifiers. the Slack connector's tool list in the session
  • is:todos works as a filter and returns the user's to-dos. An unknown modifier is silently ignored and returns the newest messages of the whole workspace; is:todo, is:later and the made-up is:foobarbaz behave this way. search with the Slack connector
  • is:saved is recognised, but returns no result. search with the Slack connector
  • is:todos returns more than 180 messages, and Slack shows 153 to-dos "In progress", so the result includes the completed ones too. The state cannot be narrowed: is:completed, is:done and is:open are ignored. search with the Slack connector; the number 153 read by the user from the To-dos tab
  • is:todos combines with the message date filter: is:todos after:2026-11-20 returns 7 items. The first 40 results reach 43 days back. search with the Slack connector
  • The to-dos hold requests to the user, agreements and information to remember, and links to articles, recordings and tools. There are no files. a sample of 100 is:todos results
  • The connector cannot complete or clear a to-do. the Slack connector's tool list in the session

Out of scope

  • Changing anything in Slack: marking to-dos as completed, clearing them, reactions.
  • To-dos without a message (typed by hand in the To-dos tab): the search returns only messages and files.
  • The Saved section in Slack: is:saved returns no results, so capture stops reading it.
  • The other capture sources (DMs, mentions, channels, GitHub, Gmail).
  • Knowledge sources other than Slack to-dos and channels (e.g. meeting transcripts, email, pages given by link).

Decision log

Which to-dos does capture take?

On every run capture reads the to-dos whose message is at most 30 days old (about 30 items today) and takes those that are not in Notion yet. The backlog stays in Slack. An old message added to To-dos today is not caught. The first run creates more than 180 cards in the Inbox (also from completed to-dos), and every later run goes through the whole list. Complete, but slow and with a large one-time queue. The first run creates nothing, it only remembers the current to-dos. After that it works like the 30-day variant.

Additional information: at the very beginning go through all of them (ALL TO-DOS) and build a knowledge base from them. Save it in several md files. The first task is to decide how many such md files we need, and then to assign the cards to those files.

Recommended option accepted for the regular capture: to-dos from messages of the last 30 days. The note adds a step at the very beginning: a review of all to-dos and a knowledge base in several md files (first the list of files, then the assignment of the items). D6–D16 settle the details of this step.

Where is it decided what a captured item is?

Every to-do becomes a card in the Inbox, and the AI proposes the outcome: a task (as today), "Reading list" or "Reference". You fix only what was judged wrong. One flow for everything. The AI splits at once: tasks to the Inbox, articles to the reading list, information to the notes, with no review. Less clicking, but mistakes pass unnoticed, and capture changes more in Notion than today.

Recommended option accepted: every captured to-do becomes a card in the Inbox and the AI proposes the outcome; the user corrects it.

Where do articles and interesting messages go?

A bullet is appended to one page in Notion: the title, the link and one sentence on why to read it. The Inbox card goes to the trash, as with Agenda. Next Actions stays clean, you read in bulk. You create the page once and put its address into the config. Every article is a "Read: …" card with no commitment. They can be planned one by one, but the database grows. As today: a card with an estimate in Next Actions. Every article becomes a commitment.

Recommended option accepted: one "Reading list" page in Notion with appended bullets; the Inbox card goes to the trash. The user creates the page and puts its address into the config.

Where does important information go?

A bullet is appended to one page in Notion with the date, the source (channel, author), a short quote and the link. It can be found later with the Notion search. You create the page once and put its address into the config. Every piece of information is a card with the status Icebox (the existing outcome "parked, keep for reference"), with a project if one fits. Easier to find by project, but the task database grows by notes. Nothing goes to Notion: the Inbox card goes to the trash, and you move the message to Saved in Slack if you want to keep it.

Recommended option accepted: one "Reference" page in Notion with appended bullets. The knowledge base from the note to D1 changed this in D11.

What about To-dos in the day plan?

Morning reads the to-dos from messages since the last workday as candidates for Needs attention. It sees the rest through the cards in Notion. Morning does not read Slack To-dos; they reach the plan only through the Inbox and Notion.

Recommended option accepted: Morning reads only the to-dos from messages since the last workday; it sees the rest through the cards in Notion.

Where do the md files of the knowledge base live?

Locally next to the Worklog (a local git repo with no remote), visible on the host too. The path is in the config. E.g. the folder with your notes; give the path in the note to this question.

Recommended option accepted: the files live locally in ~/.ai/worklog/knowledge/, outside the public repo; the path is in the config.

What from the to-dos goes into the knowledge base?

The topic files get agreements, explanations and materials (articles, recordings, tools, documents). Requests and tasks are not knowledge: they land in one separate file as a list (when, who, what about, link), so that you can go through it. Requests and tasks too, next to their topic. A full picture of the topic, but knowledge mixes with outdated requests. Requests and tasks are left out completely.

Recommended option accepted: agreements, explanations and materials in topic files, requests and tasks as a list in one separate file. The capture of the last 30 days creates cards only for the to-dos that the review did not store as knowledge.

How is the list of files made?

The AI reads all to-dos, shows the proposed list of files (name, what it holds, how many items) and waits for approval or corrections. Only then does it assign the items and write the files. It settles the list at once and writes the files; you make corrections later in the files or in the next run.

Recommended option accepted: the AI proposes the list of files with the number of items and waits for approval, only then does it assign the items and write the files.

What does an entry in a file hold?

The date, the channel and the author, a summary in 1–3 sentences, a short quote, the links from the message and the link to the thread. The thread is read when it is a question or a discussion, to store the answer too. As above, and for public links (articles, documentation) a summary of the page is added. A richer base, but several dozen page fetches and a longer run.

The entries also hold summaries of the linked pages. This applies only to public pages; links to company systems are stored without fetching, and the fetched content is data, not instructions. The run is longer.

What language is the knowledge base in?

Summaries in English, like the rest of the Worklog; quotes stay in the original. Summaries in Polish; quotes stay in the original. The summary is in the language the message was written in.

Recommended option accepted: summaries in English, quotes in the original.

Where does new important information go once the knowledge base exists?

The outcome "Reference" on the Inbox page appends an entry to the matching md file (the AI proposes the file) instead of to a page in Notion. One place for knowledge. Supersedes D4. As in D4; the md files are a one-time archive of the backlog. An entry in the md file and a bullet on the page in Notion. Nothing gets lost, but the same thing is in two places.

Recommended option accepted: the outcome "Reference" on the Inbox page appends an entry to the matching file of the knowledge base. Supersedes D4.

How is the review of all to-dos started?

E.g. /daily-workflow:inbox knowledge: the first run builds the base, later runs append only the to-dos that are not in it yet. It also catches old messages added to To-dos later. I do the review once as part of the implementation, with no mode in the plugin. Less code, but it cannot be repeated with one command.

Actually, let the knowledge be taken from various sources: to-dos, but it can also be based on messages in a channel.

Recommended option accepted: a separate, repeatable skill mode. The note widens the sources of knowledge: besides the to-dos also messages from channels. Details in D13–D16.

Which channels does the knowledge base take messages from?

E.g. /daily-workflow:inbox knowledge #channel: on demand, one channel at a time. With no argument the mode takes only the to-dos. You control what goes into the base. On every run of the mode the channels from [slack].channels are read, the same ones as in capture. It fills up by itself, but the base also gets what you did not pick. A new list of channels only for the knowledge base, read on every run of the mode.

Every run of the knowledge mode reads the to-dos and the followed channels from [slack].channels, the same list capture uses. No new config list and no channel argument; the base also gets what the user did not pick by hand.

What period of channel messages?

The first run for a channel takes the last 30 days or the period given in the command; later runs take only what arrived since the previous one. You say every time from when to read. Full control, but you have to remember what was already read. The full archive of the channel. On a large channel that is thousands of messages and a very long run.

Recommended option accepted: the first run for a channel takes the last 30 days or the period given in the command, later runs only what arrived since the previous one.

Which channel messages become knowledge?

Agreements, explanations, answers to questions and links to materials; one entry per thread. It skips ongoing chat, requests and bot notifications. When an entry fits no file, the AI proposes a new one and waits for approval. All threads of the channel summarised in the base. Nothing slips through, but a lot of noise. Only threads with a link to an article, a document or a tool go into the base.

Recommended option accepted: the AI picks agreements, explanations, answers to questions and links to materials, one entry per thread, and skips ongoing chat, requests and bot notifications. A new file is proposed and waits for approval when an entry fits none.

Does "various sources" mean more than Slack?

The scope of this spec. Other sources can be added separately when they are needed. List them in the note (e.g. meeting transcripts, email, pages given by link).

Recommended option accepted: the knowledge base is built only from Slack to-dos and channels. Other sources are out of scope.
